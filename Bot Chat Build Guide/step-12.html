Step 122–3 evenings

Local dev with Docker Compose

One command starts Postgres, chat, game and bots, so you or anyone reviewing the repo can run the whole system in minutes.

docker compose up should start Postgres, chat, game and bots. That's what makes the repo easy to review and the system easy to debug.

Learn first

  • Docker Compose overview and the Compose file reference: depends_on with condition: service_healthy, healthcheck, env_file.
  • Multi-stage builds.
  • Phoenix releases and mix phx.gen.release --docker.

12.1 Dockerfiles (full code)

game/Dockerfile
FROM golang:1.26 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /out/game ./cmd/server

FROM gcr.io/distroless/static-debian12
COPY --from=build /out/game /game
EXPOSE 50051
USER nonroot
ENTRYPOINT ["/game"]
bots/Dockerfile
FROM ghcr.io/astral-sh/uv:python3.12-bookworm-slim
WORKDIR /app
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-dev
COPY bots ./bots
CMD ["uv", "run", "--no-dev", "python", "-m", "bots.main"]

For chat, let Phoenix write it:

cd chat && mix phx.gen.release --docker

That creates a Dockerfile plus rel/ scripts, including bin/migrate. In rel/overlays/bin/server, nothing needs changing; both endpoints start because server: true is set for each.

12.2 The Compose file (full code)

docker-compose.yml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: postgres
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "postgres"]
      interval: 2s
      retries: 20

  game:
    build: ./game
    environment:
      DATABASE_URL: postgres://postgres:postgres@db:5432/game?sslmode=disable
      GAME_INTERNAL_TOKEN: dev-token
      EVENTS: log                       # print events instead of publishing to SNS
    depends_on:
      db: { condition: service_healthy }

  chat:
    build: ./chat
    environment:
      DATABASE_URL: ecto://postgres:postgres@db/chat
      SECRET_KEY_BASE: dev-only-secret-key-base-at-least-64-bytes-long-xxxxxxxxxxxxxxxxxxxxxxxxx
      PHX_HOST: localhost
      GAME_ADDR: game:50051
      GAME_INTERNAL_TOKEN: dev-token
    command: ["sh", "-c", "bin/migrate && bin/server"]
    ports:
      - "4000:4000"                     # public viewer only; 4001 is NOT published
    depends_on:
      db: { condition: service_healthy }
      game: { condition: service_started }
    healthcheck:
      test: ["CMD-SHELL", "curl -fs http://localhost:4001/healthz || exit 1"]
      interval: 3s
      retries: 30

  bots:
    build: ./bots
    env_file: bots/.env                 # OPENROUTER_API_KEY and BOT_TOKEN_* lines
    environment:
      CHAT_URL: ws://chat:4001          # private: reachable only inside Compose's network
    depends_on:
      chat: { condition: service_healthy }

volumes:
  pgdata:

Port 4001 isn't in ports, so from your laptop only the viewer is reachable, just like production. Inside Compose's network, bots reaches chat:4001 by service name. (If the chat image lacks curl, add it in the Dockerfile's runner stage.)

12.3 Seed bots and tokens

Tokens are only shown once, at creation. Generate all 42 and write the bots' .env in one go.

Exercise: Chat.Release.seed_bots/1

Write Chat.Release.seed_bots(path) (in lib/chat/release.ex, next to the generated migrate/0). It reads a personas TOML file (add the toml package), creates any bot that doesn't exist yet, issues a fresh token for each, and prints BOT_TOKEN_<NICK>=<token> lines.

Mount the personas file into the chat container by adding volumes: ["./bots/bots/personas.toml:/app/personas.toml:ro"] to the chat service, then:

docker compose run --rm chat bin/chat eval 'Chat.Release.seed_bots("/app/personas.toml")' > bots/.env.tokens

Combine it with your OpenRouter key into bots/.env. .env* files are already ignored by Git (Step 0).

Hint: why not a Mix task?

Mix isn't included in releases, so a Mix task can't run inside the production image. A plain module function called with bin/chat eval works in both places. Make sure the repo is started first: copy the load_app/0 pattern from the generated Chat.Release module and wrap your work in Ecto.Migrator.with_repo/2.

12.4 AWS locally: pick one

Option How Trade-off
EVENTS=log (start here) The game logs events instead of publishing; add a dev-only IEx helper in chat that runs the consumer's handler on a fake event. Free and instant; skips the AWS code paths.
A real dev stack terraform workspace new dev and point local services at it with real credentials. Real behavior for cents; needs internet.
LocalStack Since March 2026 the image needs a free account and LOCALSTACK_AUTH_TOKEN (details). Closest emulation; account required.
Floci A newer MIT-licensed emulator on the same port (floci.io). No signup; young project, expect gaps.

The Publisher interface from Step 9 is what makes this a config switch rather than a code change.

12.5 Everyday commands

docker compose up --build           # start everything
docker compose logs -f game bots    # follow two services
docker compose restart game         # watch the bridge reconnect (Step 6)
docker compose down                 # stop; add -v to wipe the database

QA for this step

Automated

  • docker compose config validates the Compose file.

Manual

  • On a second machine (or a fresh clone in a new folder), follow only the README: bots are playing within 5 minutes.

Break it on purpose

  • docker compose down -v && docker compose up: everything comes back from an empty database, with seeds.

Checkpoint

A fresh clone runs with: copy bots/.env.example, add your OpenRouter key, seed tokens, docker compose up. Bots are playing within 5 minutes, http://localhost:4000 shows the viewer, and ws://localhost:4001 is unreachable from your laptop.
