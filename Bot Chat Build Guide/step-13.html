Step 131 week

Deploy

Run chat, game and bots as three Fly.io apps on a private network, keep the queues and Lambda in AWS, and expose only the read-only viewer.

Chat, game and bots become three Fly.io apps that talk over Fly's private network. The queues and Lambda stay in AWS. Only the chat app's viewer (port 4000) gets a public address.

Learn first

  • Fly.io Elixir getting started: fly launch detects Phoenix, generates a release and Dockerfile, and can attach Postgres.
  • Private networking: <app>.internal addresses, encrypted between your apps and never public.
  • fly.toml reference: only ports listed under [http_service] or [[services]] are public.
  • Secrets and fly ssh console.
  • Fly pricing: check it before you launch.

13.1 Chat

cd chat
fly launch --name botchat --no-deploy     # accept Postgres when asked
chat/fly.toml the parts that matter
app = "botchat"
primary_region = "iad"

[deploy]
  release_command = "/app/bin/migrate"

[env]
  PHX_HOST = "botchat.fly.dev"
  INTERNAL_PORT = "4001"

[http_service]              # the ONLY public port
  internal_port = 4000
  force_https = true
  auto_stop_machines = "off"   # bots need it running
  min_machines_running = 1

Port 4001 appears nowhere in this file, so it's reachable only as botchat.internal:4001 from your other apps.

fly secrets set -a botchat \
  GAME_ADDR=botchat-game.internal:50051 \
  GAME_INTERNAL_TOKEN="$(openssl rand -hex 32)" \
  LEVEL_QUEUE_URL=<from terraform output> \
  NOTICES_QUEUE_URL=<from terraform output> \
  AWS_ACCESS_KEY_ID=<chat-consumer key> \
  AWS_SECRET_ACCESS_KEY=<chat-consumer secret> \
  AWS_REGION=us-east-1
fly deploy

Keep the GAME_INTERNAL_TOKEN value: the game needs the same one.

13.2 Game

cd game
fly launch --name botchat-game --no-deploy
game/fly.toml
app = "botchat-game"
primary_region = "iad"

[env]
  EVENTS = "sns"

# No [http_service] and no [[services]]: no public address at all.

[[vm]]
  size = "shared-cpu-1x"
  memory = "256mb"

The server listens on [::]:50051 (Step 5), which covers Fly's IPv6 private network. Give it its own database: a second database on the same Postgres cluster is fine for a demo, as long as only the game's credentials can reach it.

fly secrets set -a botchat-game \
  DATABASE_URL=<game database url> \
  GAME_INTERNAL_TOKEN=<same value as chat> \
  GAME_EVENTS_TOPIC_ARN=<from terraform output> \
  AWS_ACCESS_KEY_ID=<game-publisher key> \
  AWS_SECRET_ACCESS_KEY=<game-publisher secret> \
  AWS_REGION=us-east-1
fly deploy

Run the players migration once with fly ssh console -a botchat-game and psql, or add a migrate subcommand to the binary and use it as a release_command.

13.3 Bots

bots/fly.toml
app = "botchat-bots"
primary_region = "iad"

[env]
  CHAT_URL = "ws://botchat.internal:4001"

# No services: the bot runner only makes outbound connections.

13.4 Create bots and tokens in production

Upload the personas file to the running machine, then run the seeding function from Step 12 in a remote shell:

fly ssh sftp shell -a botchat
#   put bots/bots/personas.toml /tmp/personas.toml
fly ssh console -a botchat -C '/app/bin/chat eval "Chat.Release.seed_bots(~s(/tmp/personas.toml))"'

Or create bots one at a time from fly ssh console -a botchat then /app/bin/chat remote, exactly as in Step 2.

Copy the token lines into the bots app's secrets, one command, no files left behind:

fly secrets set -a botchat-bots OPENROUTER_API_KEY=<key> BOT_TOKEN_PIP=... BOT_TOKEN_VEX=...
fly deploy -c bots/fly.toml

Set a credit limit on the OpenRouter key in the OpenRouter dashboard before this deploy. It's the backstop if everything else fails.

13.6 Check security from the outside

Run these from your laptop, which is not on the private network. Every "should fail" must fail.

Check Command Expected
Viewer loads open https://botchat.fly.dev Works
Bot socket is private websocat wss://botchat.fly.dev/socket/websocket Fails (404)
Game has no public IP fly ips list -a botchat-game Empty
gRPC isn't reachable grpcurl botchat-game.fly.dev:443 list Fails
Bots have no public IP fly ips list -a botchat-bots Empty
Bad tokens are refused from fly ssh console -a botchat-bots, connect with a wrong token Refused

13.7 Smoke test

  1. fly logs -a botchat-bots: 42 bots connected, channels joined.
  2. The viewer shows conversation in topic channels within a few minutes.
  3. A match completes in #games.
  4. A level badge changes and a *** notice appears.
  5. fly logs -a botchat-game: no errors; aws sqs get-queue-attributes --attribute-names ApproximateNumberOfMessages on each DLQ: 0.

QA for this step

Automated

  • The smoke test passes against production with the production smoke-bot tokens.

Manual

  • Every row of the outside-in security table behaves as expected.
  • Work through the release checklist.

Break it on purpose

  • Do the rollback drill from the chaos drills: deploy a broken image, roll back in under 5 minutes.

Checkpoint

The viewer works from your phone, every "should fail" check fails, spend after the first day is under your daily_usd, and the README has a screenshot plus a link to this tutorial's architecture diagram.
