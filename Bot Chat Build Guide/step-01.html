Step 11–2 weeks

Learn Elixir basics

Learn enough Elixir to build a chat room as a GenServer: pattern matching, processes, OTP and tests.

Elixir runs on the BEAM, Erlang's virtual machine. You build systems from many tiny isolated processes that only talk by sending messages. That's the same idea as microservices, inside one program, and it's why chat is written in Elixir.

Learn first

  1. Getting Started guide: basic types, pattern matching, case/cond/with, modules and functions, recursion, Enum, the pipe |>.
  2. Processes: spawn, send, receive.
  3. The Mix & OTP guide chapters on GenServer and supervisors.
  4. Practice: 15–20 exercises on the Exercism Elixir track.
  5. Skim what Elixir 1.20's type inference means so new compiler warnings make sense.

1.1 Pattern matching in iex

Open the interactive shell with iex and try these. = is not assignment; it's a match.

iex> {:ok, nick} = {:ok, "pip"}
{:ok, "pip"}
iex> nick
"pip"
iex> {:ok, _} = {:error, :timeout}
** (MatchError) no match of right hand side value: {:error, :timeout}

iex> "!join" <> rest = "!join now"
iex> rest
" now"

iex> %{nick: n} = %{nick: "vex", level: 3}
iex> n
"vex"

You'll use the string-prefix match constantly: "room:" <> room = socket.topic pulls the room name out of a channel topic.

1.2 Functions with multiple clauses

Elixir picks the first clause whose pattern matches. This replaces most if chains.

defmodule Feedback do
  def for_guess(secret, secret), do: :correct
  def for_guess(secret, guess) when guess < secret, do: :higher
  def for_guess(_secret, _guess), do: :lower
end

Feedback.for_guess(38, 50)  #=> :lower

The first clause only matches when both arguments are the same value. when adds a guard.

Exercise: parse chat commands

Write Command.parse/1 that turns a chat line into a tuple, using only function clauses and string-prefix matches:

  • "!join" → :join
  • "!start" → :start
  • "42" → {:guess, 42} (use Integer.parse/1)
  • anything else → :chat
Hint

Integer.parse("42") returns {42, ""}; Integer.parse("42abc") returns {42, "abc"}. Match on {n, ""} inside a case to accept only whole numbers.

1.3 Processes and messages

Every process has a mailbox. send drops a message in; receive takes one out.

pid = spawn(fn ->
  receive do
    {:hello, from} -> send(from, {:hi, self()})
  end
end)

send(pid, {:hello, self()})

receive do
  {:hi, other} -> IO.puts("got a reply from #{inspect(other)}")
after
  1_000 -> IO.puts("no reply")
end

Processes share no memory. If one crashes, the others keep running. That's the property the whole chat service relies on.

1.4 A chat room as a GenServer

Hand-rolling receive loops gets old fast. A GenServer is the standard shape: a process that holds state and handles requests one at a time. Create a practice project:

mix new room_lab --sup
cd room_lab

Here is the skeleton. The client API and init/1 are done; the two callbacks are yours.

lib/room_lab/room.ex
defmodule RoomLab.Room do
  use GenServer

  # ---- Client API: what other code calls ----
  def start_link(name), do: GenServer.start_link(__MODULE__, name)
  def join(room, nick), do: GenServer.call(room, {:join, nick})
  def say(room, nick, text), do: GenServer.call(room, {:say, nick, text})
  def history(room), do: GenServer.call(room, :history)

  # ---- Server callbacks: run inside the room's own process ----
  @impl true
  def init(name) do
    {:ok, %{name: name, members: MapSet.new(), messages: []}}
  end

  @impl true
  def handle_call({:join, nick}, _from, state) do
    {:reply, :ok, %{state | members: MapSet.put(state.members, nick)}}
  end

  def handle_call(:history, _from, state) do
    {:reply, Enum.reverse(state.messages), state}
  end

  # Exercise: add handle_call({:say, nick, text}, _from, state)
end

Exercise: implement say

Add a handle_call({:say, nick, text}, _from, state) clause that:

  1. Replies {:error, :not_joined} if nick isn't a member, without changing state.
  2. Otherwise prepends {nick, text} to messages and replies :ok.
  3. Keeps at most 100 messages.

Why prepend and reverse in history/1? Prepending to a list is O(1); appending is O(n).

Hint: checking membership

MapSet.member?(state.members, nick) returns a boolean. Use it in a guard-free if, or split into two clauses with a helper.

One possible solution 
def handle_call({:say, nick, text}, _from, state) do
  if MapSet.member?(state.members, nick) do
    messages = Enum.take([{nick, text} | state.messages], 100)
    {:reply, :ok, %{state | messages: messages}}
  else
    {:reply, {:error, :not_joined}, state}
  end
end

1.5 Test it with ExUnit

Tests are how you'll know each step works. Write them as you go.

test/room_lab/room_test.exs
defmodule RoomLab.RoomTest do
  use ExUnit.Case, async: true
  alias RoomLab.Room

  setup do
    {:ok, room} = Room.start_link("#general")
    %{room: room}
  end

  test "members can talk and history is in order", %{room: room} do
    :ok = Room.join(room, "pip")
    :ok = Room.say(room, "pip", "hi")
    :ok = Room.say(room, "pip", "anyone here?")
    assert Room.history(room) == [{"pip", "hi"}, {"pip", "anyone here?"}]
  end

  test "non-members are rejected", %{room: room} do
    assert {:error, :not_joined} = Room.say(room, "ghost", "boo")
  end
end

mix test

Exercise: write the 100-message test

Add a test that sends 150 messages and asserts length(Room.history(room)) == 100 and that the first entry is message 51.

1.6 Supervision: let it crash

Supervisors restart processes that die. Register rooms by name and start them under a DynamicSupervisor:

lib/room_lab/application.ex
def start(_type, _args) do
  children = [
    {Registry, keys: :unique, name: RoomLab.Registry},
    {DynamicSupervisor, name: RoomLab.RoomSup, strategy: :one_for_one}
  ]

  Supervisor.start_link(children, strategy: :one_for_one, name: RoomLab.Supervisor)
end

# In Room: register by name so callers don't need the pid
def start_link(name),
  do: GenServer.start_link(__MODULE__, name, name: {:via, Registry, {RoomLab.Registry, name}})

def via(name), do: {:via, Registry, {RoomLab.Registry, name}}

Try it in iex -S mix:

DynamicSupervisor.start_child(RoomLab.RoomSup, {RoomLab.Room, "#general"})
pid = GenServer.whereis(RoomLab.Room.via("#general"))
Process.exit(pid, :kill)
GenServer.whereis(RoomLab.Room.via("#general"))   # a new pid: it was restarted

What restarting costs you

The restarted room has empty history: state lived in the process. In Step 2 messages move to Postgres, so a crash loses nothing. Deciding what can be lost on a crash is a design question you'll meet again in the game service.

QA for this step

Automated

  • mix test covers join, say, non-member rejection and the 100-message cap.
  • A concurrency test: 1,000 Task.async calls to say/3 at once, then history/1 has exactly 100 entries and the process is still alive.

Manual

  • In iex -S mix, kill a room and confirm the supervisor restarts it under the same name.

Break it on purpose

  • Send the room a message it doesn't handle (send(pid, :junk)) and read the log: decide whether that should crash it.

Checkpoint

mix test passes, including your 100-message test, and you can explain two things in your own words: the difference between call and cast, and why the room's state can't get corrupted even when 1,000 processes call it at once.
