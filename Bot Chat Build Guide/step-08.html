Step 81–2 evenings

AWS foundations

Set up an AWS account safely: locked-down root, single sign-on for daily use, a CLI with no long-lived keys, and a budget alarm.

Set the account up safely before you create anything. Then a mistake costs you an email, not a bill.

Learn first

  • Create an AWS account and the current Free Tier terms (they changed in 2025; read them).
  • Root user best practices.
  • IAM Identity Center getting started.
  • AWS CLI v2 install and SSO with the CLI.
  • IAM security best practices, especially least privilege.

8.1 Lock down the root user

  1. Create the account with an email you'll keep forever.
  2. In Security credentials, turn on MFA for the root user (a passkey or authenticator app).
  3. Don't create access keys for root. From now on you only sign in as root to change billing or close the account.

8.2 A daily login with IAM Identity Center

  1. Open IAM Identity Center and enable it in the region you'll use for everything (this guide uses us-east-1).
  2. Create a user for yourself.
  3. Create a permission set from the AdministratorAccess managed policy. That's fine for a personal sandbox; services will get tiny, specific permissions in Step 11.
  4. Assign your user to your AWS account with that permission set.
  5. Sign in through the AWS access portal URL Identity Center shows you. Bookmark it.

8.3 The CLI without long-lived keys

aws configure sso
#   SSO session name: botchat
#   SSO start URL:    <your access portal URL>
#   SSO region:       us-east-1
#   (a browser opens; approve, then pick the account and AdministratorAccess)
#   CLI profile name: botchat

aws sso login --profile botchat
aws sts get-caller-identity --profile botchat
export AWS_PROFILE=botchat      # add to your shell profile

get-caller-identity should print your account ID and an assumed-role ARN. The credentials it uses expire after a few hours; aws sso login renews them. Nothing secret sits in ~/.aws/credentials.

8.4 A budget alarm

ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)

aws budgets create-budget --account-id "$ACCOUNT_ID" \
  --budget '{"BudgetName":"botchat-monthly","BudgetLimit":{"Amount":"10","Unit":"USD"},
             "TimeUnit":"MONTHLY","BudgetType":"COST"}' \
  --notifications-with-subscribers '[
    {"Notification":{"NotificationType":"ACTUAL","ComparisonOperator":"GREATER_THAN","Threshold":50},
     "Subscribers":[{"SubscriptionType":"EMAIL","Address":"you@example.com"}]},
    {"Notification":{"NotificationType":"FORECASTED","ComparisonOperator":"GREATER_THAN","Threshold":100},
     "Subscribers":[{"SubscriptionType":"EMAIL","Address":"you@example.com"}]}]'

You'll get an email at 50% of $10 actual spend and when the month is forecast to pass $10. SNS, SQS and Lambda at this project's volume cost cents a month, so an alert means something is wrong.

8.5 Tour SNS and SQS by hand

Do this once in the CLI so the Terraform in Step 11 makes sense. Then delete everything.

TOPIC=$(aws sns create-topic --name tour-events --query TopicArn --output text)
QUEUE_URL=$(aws sqs create-queue --queue-name tour-queue --query QueueUrl --output text)
QUEUE_ARN=$(aws sqs get-queue-attributes --queue-url "$QUEUE_URL" \
  --attribute-names QueueArn --query Attributes.QueueArn --output text)

# Allow this topic (and only it) to send to the queue. Needs jq (brew/apt install jq).
POLICY=$(jq -cn --arg q "$QUEUE_ARN" --arg t "$TOPIC" '{
  Version: "2012-10-17",
  Statement: [{Effect: "Allow", Principal: {Service: "sns.amazonaws.com"},
    Action: "sqs:SendMessage", Resource: $q,
    Condition: {ArnEquals: {"aws:SourceArn": $t}}}]}')
jq -n --arg p "$POLICY" '{Policy: $p}' > /tmp/attrs.json
aws sqs set-queue-attributes --queue-url "$QUEUE_URL" --attributes file:///tmp/attrs.json

aws sns subscribe --topic-arn "$TOPIC" --protocol sqs --notification-endpoint "$QUEUE_ARN" \
  --attributes RawMessageDelivery=true

aws sns publish --topic-arn "$TOPIC" --message '{"hello":"queue"}'
aws sqs receive-message --queue-url "$QUEUE_URL" --wait-time-seconds 5

You should see your JSON in Body. Run receive-message again within 30 s: nothing. Wait 30 s and run it again: the same message is back, because you never deleted it. That's the visibility timeout, and it's why consumers must delete messages after processing and must be idempotent.

aws sns delete-topic --topic-arn "$TOPIC"
aws sqs delete-queue --queue-url "$QUEUE_URL"

Exercise: break it on purpose

Repeat the tour without RawMessageDelivery=true and compare the message body: you'll see SNS's JSON envelope wrapping your message. Then remove the queue policy and publish again: the message silently never arrives. Remember both when something "just doesn't work" later.

QA for this step

Automated

  • aws iam get-account-summary --query 'SummaryMap.AccountAccessKeysPresent' returns 0 (no root access keys).

Manual

  • Trigger the budget alert by temporarily lowering the budget below current spend; confirm the email arrives, then restore it.

Break it on purpose

  • Run the SNS/SQS tour without the queue policy and confirm the message silently doesn't arrive: now you'll recognize the symptom.

Checkpoint

aws sts get-caller-identity works with no access keys on your machine, root has MFA, the budget exists, and you've seen a message go from SNS to SQS and reappear after its visibility timeout.
