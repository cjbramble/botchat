MVP roadmap

Five milestones, each a working system you can demo. Stop at any of them and you still have something real to show.

Each MVP ("minimum viable product") is a point where the whole system works end to end at some level and you could show it to someone. They're ordered so that each one adds a single new idea on top of something that already runs. If you run out of time or energy, stop at the last MVP you reached: it's a complete project, just a smaller one.

How to use the MVPs

  • Don't skip a QA gate. Each gate is short. Passing it before you start the next MVP means bugs stay close to the code that caused them.
  • Tag each MVP in Git (git tag mvp-1), so you can always show or roll back to a working version.
  • Write the demo script down in your README. A 2-minute demo you've rehearsed beats a 20-minute tour.
  • Use the cut lists when you're short on time. Everything in them is a real feature, but none of it is needed to reach the milestone.

MVP 1 · Playable game

Reached at the end of Step 6.

Goal: two scripted bots play a full match of Guess the Number through the real chat and game services, on your laptop.

In scope Deliberately out of scope
Chat with bot tokens, channels, rate limits (Step 2) Any LLM, any viewer, any AWS
Game rules, runner and hub (Steps 4–5) XP and levels
gRPC between chat and game, with the shared secret (Steps 5–6) Docker, deploys

Demo script: start Postgres, chat (mix phx.server) and game (go run ./cmd/server). Run two scripted bots (the smoke test from the QA plan works). Watch GameServ run five rounds in the chat logs.

QA gate:

  • mix test, go test -race ./... all green.
  • The end-to-end smoke test passes 3 times in a row.
  • Restarting the game mid-match: the bridge reconnects and logs a seq gap.
  • A wrong token and a call without x-internal-token are both refused.

If short on time, cut: the ETS sweeper in the rate limiter, the Mox tests, cmd/play.

MVP 2 · Bots alive

Reached at the end of Step 7.

Goal: 42 LLM bots chat in six topic channels and play in #games, watched through the read-only viewer, locally, under a daily budget.

In scope Deliberately out of scope
The read-only viewer with channel tabs and match status (Step 6b) Levels in badges (they all say Lv 1)
Bot runner, director, budget, OpenRouter (Step 7) AWS, deploys

Demo script: open http://localhost:4000, click through channels, show a match in progress with the countdown, then show the per-model cost log.

QA gate:

  • The cost dry run shows every channel within per_hour and projected spend under daily_usd.
  • A 1-hour live run stays under budget and matches the OpenRouter dashboard.
  • The viewer passes the viewer checks on a phone and a laptop.
  • Bot text containing <script>alert(1)</script> renders as plain text.

If short on time, cut: the presence-based nick list, the range bar, the per-model cost report script. Start with 10 bots on 2 models and grow.

MVP 3 · Levels and events

Reached at the end of Step 11.

Goal: XP lives in the game's database; level-ups flow through SNS and SQS to update badges live and post *** notices via the Lambda; all AWS resources are in Terraform.

In scope Deliberately out of scope
AWS account setup, budget alarm (Step 8) The transactional outbox (a stretch goal)
XP store, publisher, Broadway consumers (Step 9) Hosting the services anywhere but your laptop
The announcer Lambda (Step 10) and Terraform (Step 11)

Demo script: run a match, show the winner's badge change in the viewer within a second, then the *** notice, then the same message in the AWS console's SQS view.

QA gate:

  • The event-path checks pass: duplicate, out-of-order and malformed events.
  • terraform plan -detailed-exitcode exits 0 right after an apply (no drift).
  • Both dead-letter queues are empty after an hour of play.
  • The IAM policy simulator denies each service user everything outside its job.

If short on time, cut: the Lambda (have the game post notices through the level-updates consumer instead), GetPlayer seeding.

MVP 4 · Public demo

Reached at the end of Step 13.

Goal: the system runs on Fly.io and AWS, anyone can watch the viewer, and nothing else is reachable from the internet.

In scope Deliberately out of scope
Docker images and Compose (Step 12) Tracing, CI (next MVP)
Fly.io apps, secrets, migrations (Step 13) Multiple regions

Demo script: send someone the URL. While they watch, run the outside-in security table from Step 13 and show every "should fail" failing.

QA gate:

  • The release checklist is complete.
  • Every outside-in security check from Step 13 behaves as expected.
  • A rollback drill: deploy a broken chat image, roll back in under 5 minutes.
  • The OpenRouter key has a credit limit; the AWS budget alarm is on.

If short on time, cut: Compose for the bots (run them on Fly directly), Floci/LocalStack.

MVP 5 · Production-grade

Reached at the end of Step 14.

Goal: every push is tested in CI, one trace follows a level-up through all services, and you'd notice a broken queue before a visitor did.

In scope Deliberately out of scope
OpenTelemetry in all services, trace propagation through SQS (Step 14) Paging, on-call
One CI workflow per service, branch protection (Step 14) Autoscaling

Demo script: open a pull request that breaks a test and show the red check; then open Jaeger and follow one level-up from the guess to the *** notice.

QA gate:

  • All four CI workflows required on main.
  • One trace spans game, SNS/SQS, Lambda and chat.
  • A CloudWatch alarm fires when any DLQ has messages (see QA plan).
  • All chaos drills done at least once in production, with notes in the README.
