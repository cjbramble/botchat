Step 21–2 weeks

Chat service in Phoenix

Build the hub: a Phoenix app with two endpoints, a public read-only one and a private one where bots connect with revocable tokens.

The chat service runs two Phoenix endpoints. The public one (port 4000) will serve only a read-only viewer. The private one (port 4001) is where bots connect, each with its own secret token. Nothing on the public side can write.

Surface Port Who can reach it What it allows
ChatWeb.Endpoint (public) 4000 Anyone Read-only LiveView (Step 6b). No login, no forms, no socket for writing.
ChatWeb.InternalEndpoint 4001 Private network only Bot WebSocket; every bot needs a valid token.
Admin — You, via a remote IEx shell Create bots, issue and revoke tokens.

Learn first

  • Phoenix Up and Running, Request life-cycle, Contexts.
  • Ecto getting started: schemas, changesets, migrations, Repo.
  • Phoenix.Endpoint: an app can run more than one.
  • Channels guide and Phoenix.ChannelTest.
  • Phoenix security guide and the OWASP WebSocket cheat sheet.

2.1 Generate the app

Postgres runs in Docker; Phoenix's generator creates the project in the empty chat/ folder.

docker run -d --name pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 postgres:17
mix archive.install hex phx_new
cd chat
mix phx.new . --app chat
mix ecto.create
mix phx.server          # http://localhost:4000 shows the Phoenix welcome page

There are no human accounts in this system, so skip mix phx.gen.auth.

2.3 One write path: Chat.Rooms.post_message/3

Every message, whatever its source, goes through one function that saves it and broadcasts it. Keeping a single write path means the bot socket, GameServ and the notice consumer (Step 10) can never behave differently.

lib/chat/rooms.ex add to the generated context
alias Phoenix.PubSub

def post_message(room, %Chat.Accounts.User{} = user, body) do
  with {:ok, msg} <- create_message(%{room: room, body: body, user_id: user.id}) do
    payload = %{
      id: msg.id,
      nick: user.nick,
      kind: user.kind,
      level: user.level_cache,
      body: msg.body,
      at: msg.inserted_at
    }

    PubSub.broadcast(Chat.PubSub, "room:" <> room, {:new_msg, payload})
    {:ok, msg}
  end
end

Exercise: recent/2 and get_channel/1

Add two more functions to Chat.Rooms:

  • recent(room, limit) returns the last limit messages for a room, oldest first, with each message's user preloaded.
  • get_channel(name) returns the channel or nil.

Then fix up Message.changeset/2: make sure it casts user_id and room (generators often leave reference fields out of cast), and validate body as required, 1–400 characters.

Hint: newest N, oldest first

Query order_by: [desc: m.inserted_at], limit: ^limit, then Enum.reverse/1 the result. Use preload: [:user] in the query (add belongs_to :user to the schema if the generator gave you a plain field :user_id).

2.4 Revocable bot tokens

Each bot gets a random token. You store only its SHA-256 hash, so a database leak doesn't leak working tokens, and deleting the row revokes it.

lib/chat/accounts.ex add
alias Chat.Accounts.BotToken

@token_bytes 32

def create_bot(nick), do: create_user(%{nick: nick, kind: "bot", level_cache: 1})

@doc "Returns the raw token ONCE. Only its hash is stored."
def issue_bot_token(%User{kind: "bot"} = user) do
  raw = :crypto.strong_rand_bytes(@token_bytes) |> Base.url_encode64(padding: false)
  Repo.insert!(%BotToken{user_id: user.id, token_hash: hash(raw)})
  raw
end

defp hash(raw), do: :crypto.hash(:sha256, raw)

Exercise: verify and revoke

Write the other two halves:

  • verify_bot_token(raw) returns {:ok, user} if a BotToken with hash(raw) exists, otherwise :error. It must also return :error for nil, empty strings and anything that isn't a binary.
  • revoke_bot_tokens(user) deletes all of that user's token rows.

Write a test for each: a valid token verifies, a revoked token doesn't, a random string doesn't.

Hint

Repo.get_by(BotToken, token_hash: hash(raw)) |> Repo.preload(:user) does the lookup. Use a function clause with when is_binary(raw) and byte_size(raw) > 0 for the happy path and a catch-all clause returning :error.

Why not Phoenix.Token?

Phoenix.Token is signed and stateless, which is great for short-lived tokens, but you can't revoke one before it expires. Bots hold their tokens for months, so a stored hash you can delete is the better fit.

2.6 The bot socket

lib/chat_web/channels/bot_socket.ex
defmodule ChatWeb.BotSocket do
  use Phoenix.Socket

  channel "room:*", ChatWeb.RoomChannel

  @impl true
  def connect(%{"token" => token}, socket, _connect_info) do
    case Chat.Accounts.verify_bot_token(token) do
      {:ok, user} -> {:ok, assign(socket, :user, user)}
      :error -> :error
    end
  end

  def connect(_params, _socket, _info), do: :error

  # Naming the socket lets you disconnect a bot instantly when you revoke it.
  @impl true
  def id(socket), do: "bot:#{socket.assigns.user.id}"
end

2.7 The room channel

lib/chat_web/channels/room_channel.ex
defmodule ChatWeb.RoomChannel do
  use ChatWeb, :channel
  alias Chat.Rooms

  @impl true
  def join("room:" <> room, _params, socket) do
    case Rooms.get_channel(room) do
      nil -> {:error, %{reason: "no_such_channel"}}
      channel ->
        send(self(), :after_join)
        {:ok, %{topic: channel.topic}, assign(socket, :room, room)}
    end
  end

  @impl true
  def handle_info(:after_join, socket) do
    Phoenix.PubSub.subscribe(Chat.PubSub, socket.topic)
    {:noreply, socket}
  end

  def handle_info({:new_msg, payload}, socket) do
    push(socket, "new_msg", payload)
    {:noreply, socket}
  end

  @impl true
  def handle_in("new_msg", %{"body" => body}, socket) when is_binary(body) do
    case Rooms.post_message(socket.assigns.room, socket.assigns.user, body) do
      {:ok, _} -> {:reply, :ok, socket}
      {:error, _changeset} -> {:reply, {:error, %{reason: "invalid"}}, socket}
    end
  end
end

Why PubSub.subscribe instead of Phoenix's built-in broadcast!? Because GameServ and the notice consumer post messages too, from outside any channel. Subscribing to the same topic post_message/3 broadcasts on means every source reaches every bot.

2.8 Server-side rate limits

The bot runner will limit itself (Step 7), but the server must not trust it. Limits differ by channel, because a game needs quick turns and conversation doesn't:

Channel Per bot Per channel
Topic channels (#general, #python, ...) 1 message per 30 s 1 message per 5 s
#games 1 message per 2 s none (GameServ's turn order already paces it)

Put these numbers in config, not in code, so the cost dry run and the server agree.

Exercise: a fixed-window rate limiter in ETS

Build Chat.RateLimit with one public function:

@spec allow?(key :: term(), limit :: pos_integer(), window_ms :: pos_integer()) :: boolean()

It counts hits for key in the current time window and returns false once limit is exceeded. Start it in application.ex (it owns the ETS table), then check the limits for the message's channel at the top of handle_in/3 and reply {:error, %{reason: "rate_limited"}} when one fails.

Hint: one counter per window

The window number is div(System.monotonic_time(:millisecond), window_ms). Use {key, window} as the ETS key and :ets.update_counter(table, ets_key, 1, {ets_key, 0}), which creates the row at 0 and increments it atomically. Create the table as :public with write_concurrency: true so callers update it directly instead of messaging a process.

Hint: cleaning up

Old windows pile up. A Process.send_after(self(), :sweep, 60_000) loop in the owning GenServer can delete rows whose window is older than the current one with :ets.select_delete/2.

One possible solution 
defmodule Chat.RateLimit do
  use GenServer
  @table __MODULE__

  def start_link(_), do: GenServer.start_link(__MODULE__, nil, name: __MODULE__)

  def allow?(key, limit, window_ms) do
    window = div(System.monotonic_time(:millisecond), window_ms)
    k = {key, window_ms, window}
    :ets.update_counter(@table, k, 1, {k, 0}) <= limit
  end

  @impl true
  def init(nil) do
    :ets.new(@table, [:named_table, :public, :set, write_concurrency: true])
    schedule()
    {:ok, nil}
  end

  @impl true
  def handle_info(:sweep, state) do
    now = System.monotonic_time(:millisecond)
    :ets.foldl(fn {{_, w_ms, w} = k, _}, acc ->
      if w < div(now, w_ms) - 1, do: :ets.delete(@table, k)
      acc
    end, nil, @table)
    schedule()
    {:noreply, state}
  end

  defp schedule, do: Process.send_after(self(), :sweep, 60_000)
end

2.9 Admin from IEx

There's no admin UI on purpose. You manage bots from a shell:

# iex -S mix   (in production: a remote shell, Step 13)
{:ok, pip} = Chat.Accounts.create_bot("pip")
token = Chat.Accounts.issue_bot_token(pip)   # copy it now; it's never shown again

# revoke + kick a live connection
Chat.Accounts.revoke_bot_tokens(pip)
ChatWeb.InternalEndpoint.broadcast("bot:#{pip.id}", "disconnect", %{})

2.10 Channel tests

test/chat_web/channels/room_channel_test.exs
defmodule ChatWeb.RoomChannelTest do
  use ChatWeb.ChannelCase
  alias Chat.Accounts

  setup do
    {:ok, bot} = Accounts.create_bot("testbot")
    token = Accounts.issue_bot_token(bot)
    {:ok, socket} = connect(ChatWeb.BotSocket, %{"token" => token})
    %{socket: socket}
  end

  test "joining a seeded channel returns its topic", %{socket: socket} do
    Chat.Repo.insert!(%Chat.Rooms.Channel{name: "python", topic: "Python", public: true})
    assert {:ok, %{topic: "Python"}, _} = subscribe_and_join(socket, "room:python", %{})
  end

  test "bad tokens can't connect" do
    assert :error = connect(ChatWeb.BotSocket, %{"token" => "nope"})
  end
end
