Step 31 week

Learn Go basics

Learn enough Go for the game service: modules, structs, interfaces, errors, goroutines, select and table-driven tests.

Go is small and statically typed. You can learn enough for this project in about a week if you write tests from day one.

Learn first

  1. A Tour of Go, all of it, including Concurrency.
  2. Tutorial: create a module and How to write Go code.
  3. Effective Go: skim now, return when unsure what's idiomatic.
  4. package testing and the table-driven tests wiki page.
  5. Go 1.26 release notes: note the rebuilt go fix and that go mod init now writes the previous minor version into go.mod.

3.1 A module and a first test

Practice in a scratch folder outside the repo:

mkdir golab && cd golab
go mod init example.com/golab
feedback/feedback.go
package feedback

// Feedback says how a guess compares to the secret.
func Feedback(secret, guess int) string {
    switch {
    case guess == secret:
        return "correct"
    case guess < secret:
        return "higher"
    default:
        return "lower"
    }
}
feedback/feedback_test.go
package feedback

import "testing"

func TestFeedback(t *testing.T) {
    cases := []struct {
        name          string
        secret, guess int
        want          string
    }{
        {"exact", 38, 38, "correct"},
        {"too low", 38, 10, "higher"},
        {"too high", 38, 90, "lower"},
    }
    for _, tc := range cases {
        t.Run(tc.name, func(t *testing.T) {
            if got := Feedback(tc.secret, tc.guess); got != tc.want {
                t.Errorf("Feedback(%d, %d) = %q, want %q", tc.secret, tc.guess, got, tc.want)
            }
        })
    }
}

go test ./...
go vet ./...

That table-driven shape is how every Go test in this project will look: one slice of cases, one loop.

3.2 Structs, methods and interfaces

An interface is a set of methods. Any type that has them satisfies it, with no implements keyword. The game uses this to describe "effects" (things that should happen) as plain values:

type Effect interface{ effect() }

type Say struct{ Text string }
type StartTimer struct{ After time.Duration }

func (Say) effect()        {}
func (StartTimer) effect() {}

func describe(e Effect) string {
    switch v := e.(type) { // a type switch
    case Say:
        return "say: " + v.Text
    case StartTimer:
        return "timer: " + v.After.String()
    default:
        return "unknown"
    }
}

The unexported effect() method means only types in this package can be Effects. That's a common Go trick for closed sets of variants.

3.3 Errors are values

Go has no exceptions. Functions return an error alongside their result, and you check it right away:

n, err := strconv.Atoi(strings.TrimSpace(text))
if err != nil {
    return nil, fmt.Errorf("not a number %q: %w", text, err)
}

%w wraps the original error so callers can inspect it with errors.Is / errors.As.

Exercise: parse a guess

Write ParseGuess(text string, lo, hi int) (int, error) that trims spaces, rejects non-integers, and rejects numbers outside lo..hi with a sentinel error ErrOutOfRange (declared as var ErrOutOfRange = errors.New("out of range")). Test it with a table, including " 42 ", "4 2", "0", "101" and "-3". Check the out-of-range case with errors.Is.

3.4 Goroutines, channels and select

A goroutine is a function running concurrently. Channels pass values between goroutines. select waits on several channels at once. Here's the exact pattern the match runner uses in Step 4: a loop that reacts to either input or a timer.

cmd/timer/main.go
package main

import (
    "bufio"
    "fmt"
    "os"
    "time"
)

func main() {
    inputs := make(chan string)
    done := make(chan struct{})

    // Reader goroutine: turns stdin lines into channel messages.
    go func() {
        sc := bufio.NewScanner(os.Stdin)
        for sc.Scan() {
            inputs <- sc.Text()
        }
    }()

    // Owner goroutine: the only code that touches `count`.
    go func() {
        count := 0
        timer := time.NewTimer(5 * time.Second)
        defer timer.Stop()
        for {
            select {
            case line := <-inputs:
                count++
                fmt.Printf("got %q (%d so far), clock reset\n", line, count)
                timer.Reset(5 * time.Second)
            case <-timer.C:
                fmt.Println("time's up after", count, "inputs")
                close(done)
                return
            }
        }
    }()

    <-done
}

go run ./cmd/timer      # type a few lines, then wait 5 seconds

Share memory by communicating

Only the owner goroutine reads or writes count, so there's no data race and no mutex. The game uses the same rule: one goroutine per match owns its state; everyone else sends it messages. Run tests with go test -race ./... to have Go catch you if you break the rule.

Exercise: a stoppable worker

Change the program so typing stop ends it immediately, and every other line is echoed back in upper case. Then add a context.Context with context.WithTimeout(ctx, 30*time.Second) and handle <-ctx.Done() as a third select case. Contexts are how gRPC (Step 5) tells your code a caller gave up.

3.5 Tools you'll run constantly

Command What it does
gofmt -w . (or your editor on save) Formats code; there's one official style.
go vet ./... Finds suspicious code (wrong Printf verbs, copied locks).
go test -race ./... Runs tests with the data-race detector.
go fix ./... Rewrites code to newer idioms (rebuilt in Go 1.26).
go doc time.Timer.Reset Docs in the terminal.

QA for this step

Automated

  • Table tests for ParseGuess pass with go test -race ./....

Manual

  • Run go vet ./... and fix everything it reports.

Break it on purpose

  • Delete the owner goroutine's rule (touch count from the reader goroutine) and watch -race catch it.

Checkpoint

Your ParseGuess table test passes with -race, the stoppable worker handles stop, input and timeout, and you can explain why one goroutine owning some state means you need no mutex.
