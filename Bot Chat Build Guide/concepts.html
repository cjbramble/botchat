Concepts primer

Five ideas carry this whole project. Read this once now, and come back whenever a later step feels confusing.

Microservices

A microservice is a small program that owns one job and its own data, and talks to others only over a network API. Here there are three: chat, game and bots. The point is not size; it's that each can be built, deployed, scaled and broken independently.

What you give up: one function call becomes a network call that can be slow, fail, or happen twice. Most of this tutorial is about handling exactly that.

Read: Martin Fowler, Microservices.

Synchronous calls vs asynchronous events

Synchronous (REST, gRPC) Asynchronous (SNS/SQS)
Shape Caller asks, waits for an answer Sender announces a fact, moves on
Example here Chat asks game: "what level is Pip?" Game announces: "Pip reached level 5"
If the other side is down The call fails; caller must cope Message waits in the queue
Number of receivers One Any number

Rule of thumb: if the caller needs the answer right now to continue, make a synchronous call with a timeout. If it's telling the world about something that already happened, publish an event.

Read: gRPC core concepts, SNS → SQS fanout.

Data ownership and eventual consistency

Only the game service writes XP and levels. Chat keeps a copy of each player's level so it can draw [Lv 4] badges without asking the game every time. That copy can be a second out of date until the level-up event arrives. This is eventual consistency: everyone agrees, eventually.

The rule that keeps it sane: every piece of data has exactly one owner, and everyone else only reads copies.

Read: microservices.io, Database per service.

Idempotency

An operation is idempotent if doing it twice has the same effect as doing it once. You need this because queues deliver messages at least once: retries, timeouts and redeliveries mean your consumer will see duplicates.

Two techniques you'll use:

  • Dedupe keys: store levelup:42:5 with a unique index; a second insert fails and you skip it.
  • Monotonic updates: UPDATE users SET level = 5 WHERE level < 5 is safe to run any number of times, in any order.

Read: SQS at-least-once delivery.

Trust boundaries

A trust boundary is a line that requests cross where you stop trusting them. This project has three: the public internet (read-only viewer only), the private network (bots, chat and game, each authenticated anyway), and AWS (reachable only with IAM credentials). Every step that adds a connection will say which boundary it crosses and how it's authenticated.

Read: OWASP Threat Modeling cheat sheet (the "what can go wrong" section).
